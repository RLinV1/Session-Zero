## Protocol and OAuth (E0/E1/E6)

- 267 MCP requests. Every request from ChatGPT's MCP client (`openai-mcp/1.0.0`, later `openai-mcp/1.0.0 (Codex)`) carried
  `MCP-Protocol-Version: 2026-07-28` and the `Mcp-Method` header; **zero `initialize` calls**. Discovery/OAuth probes came from
  `Python/3.14 aiohttp/3.14.4`.
- ChatGPT read protected-resource metadata, then `/.well-known/oauth-authorization-server`, and also tried
  `/.well-known/openid-configuration`. Because the stub answered that path, the connector form enabled **OIDC by default**;
  it was turned off by hand and the stub no longer answers it (`90e11bc8`).
- The connector form showed "CIMD is unavailable because the server did not advertise CIMD support" and chose **DCR**.
  Registration: `client_name: "ChatGPT"`, `redirect_uris: ["https://chatgpt.com/connector_platform_oauth_redirect"]`,
  `token_endpoint_auth_method: "none"` (public client + PKCE), grant types `authorization_code`, `refresh_token`.
- Authorization request: `response_type=code`, `scope=studio:m0`, `code_challenge_method=S256`, `state`,
  `resource=…/mcp/studio-m0`, `ui_locales=en-US`. The token request repeated `resource`. The authorize page opened in the
  **same tab** and returned to the originating page or conversation.
- ChatGPT's own consent dialog states that app data "may be used to improve our models" when the user's
  *Improve the model for everyone* setting is on.
- After the server-side access token was expired (operator `expire-access`, 10:04:12Z): the next view call got 401, ChatGPT
  re-ran discovery and showed a **reconnect modal over the view**. It did **not** attempt the `refresh_token` grant. The view
  kept its last state with a "stale — retrying" badge; no bytes were returned with the expired token (29 bearer requests
  refused overall). Reconnecting restored the same workspace in the same conversation.
- `revoke-all` behaved the same. Reconnecting as `m0-tester-b` made every call naming tester A's workspace fail with
  "No workspace with that id" and no image bytes.
- A model-initiated call after a server restart showed an **inline "Reconnect … connection has expired" card** instead of
  the modal. In one case the model retried the tool after reconnecting; in another it did not.
- App-originated (`visibility: ["app"]`) calls reached the server with the same bearer and subject as model calls.

## View rendering and templates (E1)

- `studio_m0_open` rendered the inline `ui://` view; host reported itself as `chatgpt`, platform `web`, display modes
  `inline`/`fullscreen` (no `pip`), view origin `https://mcp-endpoint-<hash>.web-sandbox.oaiusercontent.com`.
- Host capabilities included `serverTools`, `serverResources`, `downloadFile`, `openLinks`, `updateModelContext`
  (text/image/resource/structuredContent), `message` (text/image/resource), and experimental `openai/message: {draft}`,
  `openai/modelContext`. `window.openai` exposed `selectFiles`, `uploadFile`, `getFileDownloadUrl`, `callTool`,
  `sendFollowUpMessage`, `requestDisplayMode`, `setWidgetState` and others.
- `requestDisplayMode({mode:"fullscreen"})` opened a large side panel beside a narrowed chat; the view received
  `host-context-changed` with `displayMode: "fullscreen"` and new container dimensions.
- **Template snapshotting:** ChatGPT pre-read the `ui://` resource when the connector was created and kept rendering that
  copy after the server changed the HTML, even after a fresh `resources/read` returned the new bytes. It did not re-list
  tools on reconnect. **Settings → Refresh tools** ran `server/discover`, `tools/list` and pre-read the new
  content-hashed URI, after which a new chat rendered the new template.
- Only CSP violations seen: `img-src` refusing `blob:` (8, all from the deliberate `blob:` probe).

## Refresh and reopen (E4)

- Model `studio_m0_set_value("lantern")` saved at 09:56:13.244Z; the already-mounted view displayed version 2 at
  09:56:15.560Z (≈2.3 s, one 5 s polling interval, no reopen). Polling paused while the view reported itself hidden.
- Reloading the conversation remounted the view, re-read the resource and **re-delivered the original tool result**
  (`initial`, v1); the first backend poll corrected it to `lantern` v2. No teardown was observed on page reload.
- Re-delivered tool results persist in the conversation after revocation or an identity change; only data the view
  fetched through app calls was gated.
